# 用户痛点与验证计划

状态：目标用户与核心场景已由用户确认；痛点强度、频率与效果仍待验证。尚未进行用户访谈或实测，不代表调研结论。

## 已确定用户与场景

目标用户包括：缺少每日信息收集时间的美股个人投资者；懂基础金融信息但缺乏系统分析方法的投资者；学习金融分析、数据分析或金融计算的学生；希望快速阅读财报和理解异动的用户。定位已确认，不等于需求已被调研证实。

1. 用户现场输入股票代码或公司名称，系统立即完成行情、技术面、基本面、新闻情绪、行业、宏观和风险分析。
2. 用户建立自选股列表，并为每只股票配置关注方向、涨跌幅阈值、成交量阈值和报告频率。系统进行分钟级异动监测，并在每日收盘后自动生成完整研究报告，通过系统消息和邮件发送。

## 待验证的痛点假设

| 假设痛点 | 场景 | 对应能力 | 验证方法 |
| --- | --- | --- | --- |
| 每天在多个网站间切换，资料分散、难以快速建立判断 | 搜到一只股票后查行情、公告和新闻 | 搜索、金融 RAG、即时分析 | 观察完成同一研究任务的步骤与耗时 |
| 信息过多，难识别真正影响股价的内容 | 筛选新闻和公告 | 事件识别与证据排序 | 观察筛选任务及用户解释 |
| 新闻与股价之间容易错误归因 | 新闻晚于价格变化仍被当作原因 | 时间审计与替代解释 | 用有来源案例检验归因过程 |
| 普通 AI 缺来源、可能胡说 | 查找金融事实 | 引用核验 | 检查事实与原文是否一致 |
| 财报太长，关键变化难找 | 阅读季度或年度报告 | 财报 RAG | 记录找关键变化的时间和遗漏 |
| 现有工具只有行情、新闻或泛泛总结 | 跨工具研究 | 连续研究流程 | 访谈实际工具链，并以竞品证据核验，不预判所有工具 |
| 持续盯盘成本高 | 多只自选股出现价格或成交量异动 | 分钟级监测 | 访谈可接受延迟与告警频率 |
| 分析容易只看单一方向 | 利好与风险证据相互冲突 | 多空、风控与裁判 | 检查用户能否解释分歧及证据 |
| 收盘后整理重复劳动多 | 汇总当天组合关注点 | 自动日报与通知 | 检查报告是否支持次日研究安排 |
| 历史观点无法追踪 | 回看之前的判断是否成立 | 历史报告与 5/20 个交易日复盘 | 检查能否找到原判断与后续变化 |

## 调研安排

遵循 Problem Discovery → 用户和痛点验证 → 竞品分析 → 用户访谈或问卷 → PRD → Prototype（原型）的已确认顺序，先明确问题及初步验证计划，再开展竞品调研和正式访谈，后续通过原型验证流程。记录样本来源、人数、时间及偏差；人数与招募方式待定。询问真实最近一次研究行为、使用工具、遗漏信息、告警容忍度、数据预算和对引用的需求，不以引导性提问证明方案正确。

产出匿名访谈记录、按频率与影响排序的问题清单，以及需求保留或调整依据。没有访谈前不写“多数用户需要”或虚构满意度。

## 本轮问题发现：要弄清楚什么

状态：验证计划已编写，尚未招募、访谈或收集用户记录。以下抽样、问题和判定方式为建议方案，不是已完成调研，也不改变已确认的两大场景与 MVP 边界。

用一句话描述要验证的问题：目标用户在研究和持续跟踪美股时，是否反复遇到信息整理、证据核查和历史判断追踪的困难，这些困难实际影响了什么？

先了解现有行为，再介绍 FinSight。不要一开始展示功能清单或问“你是否需要我们的 AI 助手”，避免受访者只是礼貌赞同。

## 分阶段执行，保留原有项目顺序

1. 问题发现：整理上面的痛点假设，准备筛选问题和空白记录模板；本轮完成此项计划准备。
2. 用户和痛点初步验证：请符合目标的用户描述最近一次实际研究经历，收集当前流程、困难和已有解决办法。不宣称完成正式访谈阶段。
3. 竞品分析：根据用户实际提到的工具，按竞品文档核验能力与限制；本轮已完成官方公开资料案头调研，但仍未做付费产品实测，也不能替代用户验证。
4. 正式访谈或问卷：结合前两步发现深入验证需求。下方提纲先行准备，后续再执行；之后才更新需求优先级、原型和技术设计。

## 建议找哪些人

建议首轮寻找 4–6 位自愿参与者，作为发现问题的小样本，不用于推断整个市场比例；人数是执行建议，不是已确认指标或实际招募人数。

覆盖两类经历：最近有美股查询或持续跟踪行为的人，以及最近读过公司财报或做过金融分析学习任务的人。尽量不要全部来自同一个朋友群。无需真实持仓，也不需要提供账户或收益。

初步筛选只问：最近一次研究美股或阅读财报是什么时候？具体研究了什么？用了哪些工具？纯粹“觉得这个项目有意思”但没有相关经历的反馈可保留为概念意见，不能当作痛点证据。

## 核心验证问题与证据

| 要验证的问题 | 可以怎样问 | 记录什么 | 什么情况会削弱假设 |
| --- | --- | --- | --- |
| 信息收集是否真的费时 | 最近一次查一家公司，你先看什么、后看什么？哪一步最费劲？ | 具体任务、工具切换、本人估计耗时或实际观察耗时，两者分开 | 现有流程顺畅，几乎没有整理成本 |
| 缺来源是否妨碍判断 | 最近有没有看到一条分析后又去找原文？为什么？ | 原结论、核查动作、能否找到出处及影响 | 用户不核查，或现有来源已足够可靠 |
| 财报阅读是否有明确困难 | 最近想从财报找什么？最后找到了吗？ | 目标信息、定位方式、遗漏与放弃原因 | 主要困难是基础知识，单纯检索未必能解决 |
| 异动提醒是否有行动价值 | 最近错过过什么信息？收到提醒后你通常会做什么？ | 真实漏看事件、现有提醒、后续研究动作、打扰情况 | 没有持续跟踪需求，或现有提醒已足够 |
| 报告是否融入日常流程 | 最近一次收盘后你查看或整理了什么？ | 实际阅读时间、报告长度、渠道与频率习惯 | 很少看收盘总结，偏好临时查询 |
| 复盘是否解决真实问题 | 最近有没有回头检查一个判断？记录在哪里？ | 原判断记录、回看方式、无法复核的原因 | 没有复盘习惯或意愿，需探索原因而非假定价值 |
| 是否存在错误归因风险 | 最近一次解释股价变化时，你怎么确定原因？有没有其他解释？ | 时间核对、证据和替代解释，不替用户判断事实真伪 | 已有成熟方法或问题更偏知识理解 |

没有具体案例时记录“尚无实例支持”，不能自动判断假设错误，也不能强迫用户编一个案例。用户提到工具缺陷后，仍需竞品核验，不能直接变成事实结论。

## 正式访谈提纲草案：后续阶段使用

建议每次约 20–30 分钟，时长是计划而非实测。

1. 说明目的：了解真实研究流程，不推销投资建议；征得记录同意，允许跳过问题，录音另行取得明确同意。
2. 请对方讲最近一次具体股票研究或财报阅读，从起因到结果，先不介绍产品。
3. 针对上述问题追问过程、困难、频率和现有解决方法；不要把全部问题机械问完。
4. 询问有没有顺利完成的反例，以及哪一步即使自动化也不希望交给系统。
5. 最后简述已确认的产品边界：只做美股研究辅助，行情可能延迟 5–15 分钟，仅正常交易时段监测，不交易、不保证收益。
6. 再问哪些任务仍适用、哪些不适用；这种反馈用于验证适配性，不自动推翻既定边界。分别询问日报/周报的“生成”和“发送”偏好，不替用户假定两者相同。
7. 问还有什么遗漏，是否愿意将来测试原型；同意访谈不等于同意邮件订阅或公开个人信息。

## 空白证据记录模板

以下是待填写字段，不是虚构访谈案例。每位真实参与者单独复制填写，不能预填人数、引语或结果。

- 匿名参与者编号：待填写。
- 日期、方式及记录授权范围：待填写。
- 所属目标用户类型及相关经历：待填写。
- 最近一次具体任务、时间及目标：待填写。
- 使用工具与实际步骤：待填写。
- 耗时及依据（本人估计/实际观察）：待填写。
- 遇到的困难、实际影响和当前解决办法：待填写。
- 原话或观察记录及定位：待填写；转述与直接引语分开。
- 支持的假设、反例及仍不清楚之处：待填写。
- 产品边界说明后的适配反馈：待填写。
- 研究者解释：待填写，不能与用户原话混为一谈。
- 允许保留或展示的材料范围：待填写。

原始联系方式、录音和未脱敏截图不进入公开仓库。只保留必要匿名记录；后续存储与保留期限按参与者授权及项目隐私规则确定。

## 如何整理结果，不预造结论

每项假设用“有初步支持 / 出现反证 / 信息不足”记录，关联真实证据编号；尚未开展研究时保持“待验证”。同时记录问题发生频率、影响、现有方案是否足够，不仅统计用户说“想要”的功能。

样本少时报告实际人数与分母，不写“市场上大多数用户”，不以小样本强行计算可信的市场占比。若证据与已确认范围冲突，提出给开发者讨论，不能自动删除核心场景或修改 MVP 决策。

本轮计划准备完成条件：问题、对象、提问方式、记录模板和真实性边界齐全。实际验证完成条件另计：有获授权的真实记录，覆盖两大场景，能追溯支持与反证，并明确未解决问题。若只有泛泛赞同或没有案例，应继续收集证据，不能进入“需求已验证”状态。
