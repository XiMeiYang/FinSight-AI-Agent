# FinSight AI Agent PRD V1.0

状态：PRD V1.0 文档整理完成，属于产品方案和待验证假设，不代表功能已经实现。当前没有真实用户访谈、API 实测、原型测试或业务代码。所有优先级均需经过真实用户验证、数据许可核验和技术验证后再调整。

## 1. 产品定位与边界

FinSight AI Agent 面向关注美股、但没有时间持续收集和整理信息的个人投资者，以及金融分析学习者。系统提供研究辅助和数据分析，不提供确定性投资建议，不承诺收益，不连接真实券商，不执行自动或真实交易。

第一阶段只做美股，允许行情存在 5–15 分钟延迟，只监控美股正常交易时段，暂不支持盘前和盘后监测。自选股数量上限、数据供应商、响应时间和评测门槛仍待确认，不能在本版写死。

## 2. 已确认的核心场景

### 场景 A：股票即时搜索与分析

用户输入股票代码、公司名称或自然语言问题，系统识别证券和时间范围，获取真实行情与基础财务数据，检索截至分析时间可用的 SEC 财报/公告和新闻，按任务复杂度调用必要工具与 Agent，生成带来源、时间、分歧、风险和限制的结构化报告。

### 场景 B：自选股监测与每日收盘报告

用户添加和管理自选股，配置关注方向、阈值和报告/通知偏好。系统在正常交易时段进行分钟级检查，发现价格、成交量、波动率、新闻或公告异常时生成简报；每日收盘后生成并保存自选股报告，首版支持系统内查看、系统消息和邮件。具体告警冷却、日报/周报生成与发送关系待确认。

## 3. 需求证据与优先级原则

- 目标用户、两个场景、数据真实性、Point-in-Time（按当时已公开信息分析）、来源展示和 5/20 个交易日复盘是已确认方向。
- 具体痛点、功能价值和优先级是**产品假设，待真实用户验证**。模拟访谈只能作为设计参考，不能写成已验证需求。
- P0 是第一个可运行演示版本必须闭环；P1 是 P0 稳定后增加；P2 是后续迭代。调整顺序不删除已确认功能。
- 竞品已较好覆盖普通 K 线、复杂 Dashboard、通用 watchlist 和基础价格告警；MVP 不把这些作为创新重点，先保证证据链和复盘闭环。

## 5. P0 用户故事

### US-01：即时分析一只股票

作为关注美股的用户，我希望输入 `NVDA` 或公司名称后看到带来源和风险的研究报告，以便快速了解当前信息，而不是在多个网站之间手动切换。

### US-02：将股票加入自选股

作为用户，我希望把已经识别的股票加入自选股并看到保存状态，以便在后续收盘报告中持续跟踪。P0 只要求添加、删除、查看和用户隔离，复杂分组和个性化规则后置。

### US-03：查看收盘报告

作为自选股用户，我希望在收盘后看到简短概览、逐股变化、证据、风险和系统限制，以便决定是否展开详细研究。报告保存后可回看；基础系统消息和邮件属于 P0，复杂频率和其他渠道后置。

## 6. P0 第一个演示闭环

`用户输入 NVDA`
→ 识别证券和交易所
→ 获取真实行情与基础财务数据，并显示数据时间和 5–15 分钟延迟状态
→ 检索截至分析时间已公开的 SEC 文件
→ Router 判断任务复杂度并调用必要 Agent
→ 行情/基本面/新闻 Agent 形成事实和计算结果
→ 多头、空头分别提出有证据的观点并保留分歧
→ Evidence Auditor 检查来源、原文位置、时间顺序和 Point-in-Time
→ Risk Agent 检查缺失数据、极端情况和过度结论
→ Judge 形成综合结论并标注置信度依据与限制
→ 生成带引用的结构化报告
→ 保存数据快照、判断、证据、模型/工具版本，供未来 5/20 个交易日复盘。

简单事实查询不强制调用全部 Agent。若只需价格或单个已核验字段，可走确定性工具；只有涉及归因、比较、财报解读或风险判断时，才扩展到检索、辩论和审计流程。

## 7. P0 详细需求与状态设计

| P0 功能 | 用户故事与流程 | 输入 | 输出 |
| --- | --- | --- | --- |
| F01 搜索识别 | 输入代码/名称 → 候选列表 → 用户确认准确证券 | query、市场=US、可选时间范围 | security_id、ticker、名称、交易所、证券类型、匹配状态 |
| F02 即时分析 | 确认证券 → 拉取数据 → 确定性计算 → 必要 Agent → 报告 | security_id、截止时间、任务类型 | 事实、计算、推断、风险四类内容及引用 |
| F03 RAG | 解析 SEC 文件 → 分块 → 检索 → 截止时间过滤 → 引用核验 | filing 类型、证券、as_of 时间、问题 | 文件、公开时间、章节/页/段定位、证据片段、检索状态 |
| F04 路由协作 | 复杂度判断 → 调用必要角色 → 审计/风控/Judge | 任务类型、数据可用性、预算 | Agent 状态、观点、分歧、审计结果、裁判结论 |
| F05 来源审计 | 检查每个重要数字和判断是否有来源及时间 | report draft、evidence、计算记录 | source_status、事实/计算/推断/风险标签、证据不足原因 |
| F06 报告保存 | 生成报告 → 保存不可覆盖的判断快照 | 报告内容、用户、版本、数据/模型/工具版本 | report_id、生成/截止时间、来源、限制、复盘到期日 |
| F07 自选股 | 从已识别证券点击加入 → 去重 → 保存 | user_id、security_id、最小配置 | watchlist item、保存状态、隔离结果 |
| F08 收盘报告 | 交易日结束 → 获取可用数据 → 对自选股汇总 → 保存 | user_id、watchlist、交易日 | 概览、逐股变化、异常、证据、风险、限制、报告状态 |
| F09 日志评测 | 每次任务写入运行记录，不伪造指标 | run_id、工具/Agent 事件 | 状态、响应时间、Token、成本依据、错误、引用状态 |
| F11 基础投递 | 用户授权 → 发送收盘报告 → 写入投递状态 | report_id、channel、recipient、idempotency_key | 待发送、已发送或失败，失败原因和重试次数 |

### P0 任务状态

- **正常状态**：`queued`（排队）、`running`（运行）、`partial`（部分完成）、`completed`（完成）。报告中显示数据截止时间、来源和行情延迟。
- **加载状态**：显示当前阶段，例如“识别证券”“读取 SEC 文件”“计算指标”“审计引用”，并允许查看已完成和待完成步骤；不显示虚构进度百分比。
- **空状态**：没有匹配证券、没有自选股、没有可用 SEC 文件、没有历史报告时，说明原因并提供下一步操作；不以零值替代缺失。
- **错误状态**：`failed`（失败）、`cancelled`（取消）、`stale`（过期）、`evidence_insufficient`（证据不足）。显示受影响的数据源、可重试性和降级结果。

### P0 验收标准

1. 输入明确的美股代码或公司名称时，能返回唯一证券或解释歧义，不把错误证券静默当成正确结果。
2. 报告中的行情、财务数字和计算结果都有数据时间、来源、币种/单位和计算口径；Agent 推断不能伪装成事实。
3. SEC 检索只使用分析截止时间前已公开且可获取的文件；没有符合条件的证据时必须输出“证据不足”。
4. 复杂任务至少保留多头、空头、Evidence Auditor、Risk 和 Judge 的输入/状态；简单查询不调用无关角色。
5. 报告能区分原始事实、确定性计算、Agent 推断和风险/不确定性，并保留支持证据、反对证据和分歧。
6. 报告保存后有唯一 `report_id` 和判断快照，不能用未来复盘结果覆盖原始报告。
7. 用户可以添加、删除和查看自选股；不同用户不能读到彼此的股票、报告或日志。
8. 收盘报告在数据不完整时标明缺失和部分完成，不伪造发送成功或完整结果。
9. 每次运行至少记录状态、开始/结束时间、响应时间、工具调用、Token/成本依据、失败原因和引用审计结果。

## 8. 数据来源与真实性

P0 的真实数据优先使用经许可核验的数据供应商；财报/公告优先 SEC EDGAR、SEC Company Facts 和公司投资者关系网站。行情供应商仍在 Alpha Vantage、Finnhub、Financial Modeling Prep、Massive 等候选中，未完成 API 测试前不得写死。新闻来源和数据许可见 [数据源方案](06-data-sources.md)。

每条数据至少保存 `source`、`event_time`、`published_at`、`retrieved_at`、`as_of`、`freshness`、币种、单位和版本。区分源延迟、采集周期和检测延迟；5–15 分钟是允许的产品模式，不代表所有供应商都满足该延迟。

## 9. 风险、降级与非功能要求

| 要求 | V1.0 约束 |
| --- | --- |
| 时间与来源 | 所有报告和图表显示数据截止时间、发布时间/事件时间、采集时间、来源和实时/延迟状态 |
| Point-in-Time | 历史任务只读当时已公开数据；保存公开时间和数据版本，不能用后续修订覆盖原判断 |
| 缺失数据 | 明确显示缺失、冲突、过期、停牌和供应商失败；关键证据缺失时阻断确定性结论 |
| 失败重试 | 适配器设置超时、有限重试、退避、幂等键和失败状态；重试不能重复报告或告警 |
| 任务恢复 | 记录阶段和 checkpoint；恢复后沿用同一 run_id，并标记重新获取的数据版本 |
| 响应时间 | 记录端到端、检索、工具和每个 Agent 的耗时；具体 SLA 待真实测试后确认 |
| Token 与成本 | 按模型、Agent、工具和任务记录 Token/成本依据；成本未知时标记未知，不估算成事实 |
| 用户隔离 | user_id 贯穿自选股、报告、证据、日志和通知；权限失败不得泄露对象存在性 |
| 安全与权限 | 不接入券商和交易工具；密钥不进日志/报告；网页、新闻和 PDF 内容视为不可信输入 |
| 通知降级 | 邮件或系统消息失败时至少保存系统内报告；标记失败，不伪报已送达 |

## 10. P1 与 P2 说明

### P1：P0 稳定后增加

分钟级正常交易时段异动监测、价格/成交量/波动率及新闻公告告警、告警冷却与合并、复杂报告频率、历史报告查询、5/20 日复盘、历史相似事件、基础 K 线/财务/新闻/行业可视化和 LLMOps 仪表。P1 的目标是把演示闭环变成可持续使用的 MVP。

### P2：后续迭代

更细的自选股分组与关注规则、多渠道通知、复杂 Dashboard、移动/Webhook、完整 Agent 表现统计、更多市场和更复杂的事件研究。所有 P2 仍保留在产品范围内，但必须由用户证据和实际运行结果证明价值。

## 11. 待确认问题

1. 真实用户最愿意为即时分析、自选股监测、财报问答和收盘报告中的哪一项付出时间或费用？
2. P0 的单只分析响应时间、收盘报告完成时限和允许的部分完成范围是多少？
3. 最终行情/新闻供应商、免费额度、许可、缓存和项目展示权限是什么？
4. SEC 文件的表格、页码/段落定位和修订版本如何统一保存？
5. 自选股上限、分钟检查周期、阈值窗口、告警冷却与邮件频率如何确定？
6. 5/20 个交易日复盘的起算点、基准、复权方法和置信度校准如何确定？
7. P0 是否需要基础图表，还是先用表格和证据卡完成可用走查？
