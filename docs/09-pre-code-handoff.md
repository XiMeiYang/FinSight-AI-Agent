# 开始写代码前：网页端 GPT 一次性任务书

状态：这是交给网页端 GPT 的准备任务，不是已完成成果。网页端 GPT 可以帮助调研、整理、分析和产出文档，但不能替代真实参与者、真实 API 测试或真实用户测试。

## 可直接复制的任务说明

先将本地项目文件或压缩包上传给网页端 GPT；GitHub 首次同步完成后，也可以提供仓库链接。网页端 GPT 必须能读取 `README.md`、`AGENTS.md`、`PROJECT_MEMORY.md`、`docs/` 和 `skills/` 后才能开始。如果无法访问这些材料，应停止并要求提供文件，不能凭聊天记忆补齐。

请以仓库文件为共享事实来源。在开始业务编码前，按下列顺序完成 FinSight AI Agent 的“开发就绪包”。保留已有正确内容，不擅自改变已确认的产品边界；所有材料明确标记为“已确认决策、建议方案、待验证假设、已验证事实、未执行或阻塞”。

### 1. 初步用户和痛点验证

- 使用 `docs/02-user-pain-points.md` 中的提纲准备招募、访谈或问卷材料。
- 由项目开发者联系真实参与者；GPT 只能整理开发者提供的匿名记录。
- 建议从 4–6 位小样本开始，这只是建议，不是硬指标或已完成数量。
- 保存支持证据、反例、当前解决方法和仍不清楚的问题，覆盖即时研究与自选股监测两个场景。
- 没有真实记录时明确写“未执行”，不能生成用户引语、人数、比例或结论。

### 2. 竞品调研

- 使用官方产品页面、定价页、帮助文档和合法试用记录，记录链接、核验日期、套餐或版本、能力、限制和证据状态。
- 比较行情图表、财经研究、通用 AI 研究、多 Agent 开源项目、自选股报告等类别。
- 未知内容写“未知”，不写虚构评分、“市场领先”或未实测的优劣。
- 对 TradingAgents 等参考项目记录许可、借鉴范围和 FinSight 自身贡献，不能复制后冒充独立成果。

### 3. 正式用户访谈或问卷

- 结合初步验证和竞品发现完善正式提纲或问卷，再由开发者招募真实目标用户并执行。
- GPT 只整理用户提供的匿名笔记、答卷和证据，不虚构受访者、引语、回答或样本量。
- 记录支持、反例、分群差异和未解决问题，并区分“用户原话、行为事实、研究者解释”。
- 尚未执行时如实标记，但该状态会阻断开发准入。

### 4. 收敛产品需求

- 用真实用户与竞品证据给痛点和需求排序，每条结论关联证据编号。
- 更新用户流程、异常状态、权限、报告字段、验收条件和待决问题。
- 保留已确认边界：MVP 只做美股；免费或低成本数据；允许 5–15 分钟行情延迟；只监控正常交易时段；不接券商、不交易、不保证收益；每日收盘报告；系统内报告/消息和邮件；5/20 个交易日复盘。
- 不擅自确定自选股上限、阈值、供应商、技术栈、置信度定义或日报/周报关系。

### 5. 原型与真实反馈

- 制作低保真原型，至少覆盖股票搜索与即时分析、自选股分组和配置、异动提醒、收盘报告、历史报告及 5/20 个交易日复盘。
- 准备可用性任务脚本，再由真实目标用户完成任务；GPT 可整理实际反馈，不能模拟用户测试。
- 记录成功、卡点、误解和修改建议；没有真实反馈时保持“未执行”。

### 6. 收敛仍待确认的产品项

- 明确或提交选择建议：界面及报告语言、美股是否含 ETF/ADR/OTC、预算和用户规模、自选股上限、检查周期、阈值和冷却、日报/周报生成与投递关系、报告时限、邮件授权与数据保留、复盘起点/基准/复权、置信度含义。
- 证据不足的项目保留待确认，不用个人偏好冒充用户结论。

### 7. 数据源证据卡与 API 测试方案

- 针对行情、SEC、FRED、新闻和交易日历候选整理官方证据卡：覆盖、免费额度、延迟、粒度、历史长度、限流、缓存、再分发、项目展示许可和 Point-in-Time 支持。
- 网页资料核验不能替代真实 API 测试。只制定最小测试矩阵，不连接 API，不宣称已接入或实测通过。
- 数据源最终选择必须等真实 API 测试后冻结。

### 8. 最小技术建议与决策记录

- 根据已经验证的真实需求提出最简单、可运行、可测试的 MVP 技术组合，并说明选择理由、替代方案和放弃理由。
- 将候选和已冻结技术分开；不为了显得复杂而一次引入所有中间件。
- 覆盖模块边界、数据契约、Point-in-Time、工具调用、多轮记忆、权限、失败恢复、LLMOps 和测试策略。
- 本任务不安装依赖、不写业务代码。

### 9. 冻结评测与基线协议

- 定义样本、标注、时间切分、Point-in-Time 检查、指标分母、失败样本处理和后续验收门槛制定方法。
- 至少保留三组：人工收集并生成报告（Baseline A）、单次大模型直接分析（Baseline B）、包含检索/工具/验证/多 Agent/复盘的 FinSight（Experiment）。
- 覆盖数据与工具、RAG、Agent、产品、LLMOps、安全及 5/20 个交易日复盘。
- 只定义方法，不填写准确率、成本、收益、提升百分比或不存在的运行结果。

### 10. 输出开发就绪包

最终交付：

1. 真实用户验证材料与匿名证据表；未执行时保留明确状态。
2. 有官方引用和核验日期的竞品矩阵。
3. 核心流程原型、测试脚本及真实反馈；未测试时明确标记。
4. PRD 修订建议及逐条证据。
5. 技术决策记录和数据源 API 测试矩阵。
6. 评测集规范与三组 Baseline 协议。
7. 按依赖排序的 MVP backlog，每项含验收条件、依赖和风险。
8. 一页开发就绪审查表，列出已完成、未执行、阻塞和待开发者决定事项。

把重要决定同步到 `PROJECT_MEMORY.md`，产品需求同步到相关 `docs/`，工作流变化才同步相应 `skills/`。不写业务代码、不安装依赖、不连接 API，不生成虚假调研、反馈、竞品结论或实验指标。

## Codex 接回后的开发准入条件

Codex 收到上述材料后先审查和合并文档。进入业务代码前至少满足：事实可追溯；用户材料真实且匿名；竞品结论有官方或合法实测证据；未验证内容仍标为假设；原型覆盖关键流程；候选与冻结技术分开；API 能力仍待真实测试；评测协议没有预填结果；所有未决问题有负责人或触发条件。

交付包允许写“未执行”，目的是如实记录状态，不代表可以通过开发准入。带来源的竞品案头调研已完成，但至少一轮真实的初步用户验证、正式用户访谈或问卷，以及原型真实反馈尚未完成时，开发就绪结论仍必须写为 `NOT READY`；样本量仍按证据质量判断，不擅自把建议人数写成硬指标。

首条建议开发主线是“离线、可追溯的单股研究闭环”。只有开发就绪审查通过后再确定工程初始化任务。
